WS-G.9

What we would do next, in priority order

  1. Alarm on failed answers, not just a live website. INC-04 showed the gap: the site was up, so the health check was green, but every answer failed for about 25 minutes. request-log.sh already writes "ok":false for each failed answer. A CloudWatch metric filter on that field and an alarm at more than 5% failed over 15 minutes (Appendix A, “AnswersFailed”) would have caught INC-04 within one evaluation period. This is about 30 minutes of work and costs nothing.
  2. Least-privilege console access. Move from one federated full-access role to IAM Identity Center: an operator permission set with MFA enforced, and admin only through a role switch. This is the first gap on the Well-Architected review.
  3. Close the CloudFront → EC2 gap. Add a secret custom header in CloudFront that the server checks, so other CloudFront distributions cannot reach port 3080. Alternatively, use a CloudFront VPC origin so the instance needs no public IP at all.
  4. Nightly evaluation as a third automation. Run app/eval.py from a systemd timer every night, publish the pass rate as a metric, and alarm if it drops below 80%. A silent model change by the provider (INC-02) would then show up the next morning.
  5. Deploy from the repository. A GitHub Actions workflow that, on a push to main, syncs app/ and content/ to S3 and runs ops.sh redeploy through an OIDC role. That replaces copying files into CloudShell by hand.

We deliberately did not list multi-AZ or a managed database. For a single-dealership demo they would roughly triple the cost, while a tested 32-second restore and a 15-minute rebuild cover the realistic failure cases.
