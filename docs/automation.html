The incidents (WS-F)

We had four real incidents. INC-01 is our main write-up, with timings and a runbook. The others are shorter.

INC-01: the app silently ignored its configuration

Started8 Nov 2026 16:12 UTC (first deploy)Noticed16:18 UTC: the login page said “LibreChat”, with no sign-up link
Fixed16:24 UTC (redeploy verified)Time to detect / fixabout 6 min / about 6 min

Symptom. The site loaded over HTTPS, but as stock LibreChat. /api/config returned "appTitle":"LibreChat", "serverDomain":"http://localhost:3080" and "registrationEnabled":false, even though we had set all three. Separately, the chat-meilisearch container was in a restart loop.

Investigation (E-15).

$ grep -E "^(APP_TITLE|DOMAIN_CLIENT|ALLOW_REGISTRATION)=" /opt/autohub/LibreChat/.env
DOMAIN_CLIENT=https://dd56jth94yne6.cloudfront.net
APP_TITLE=AutoHub Assistant
ALLOW_REGISTRATION=true                      <- the file on the host is correct
$ docker exec LibreChat printenv APP_TITLE ALLOW_REGISTRATION
                                             <- …but the container sees nothing
$ grep -A3 "source: ./.env" docker-compose.yml
        source: ./.env
        target: /app/.env                    <- .env is bind-mounted, and the app runs as user "${UID}:${GID}" = 1000
$ docker logs --tail 2 chat-meilisearch
Error: Permission denied (os error 13)       <- same pattern: meili_data_v1.35.1 owned by root

Root cause. Our start-autohub.sh ran as root and wrote .env with install -m 600, so the file was owned by root and readable only by root. The LibreChat container runs as uid 1000 and reads /app/.env through a bind mount. It could not read the file and silently fell back to its defaults. For the same reason Docker created Meilisearch's data folder as root, and the search service, also running as uid 1000, crashed on every start.

Fix and prevention. start-autohub.sh now writes install -m 600 -o 1000 -g 1000 .env.new .env, so the file is still private but owned by the app's user. It also pre-creates and chowns the Meilisearch data folder (its name is read from the compose file, so a LibreChat upgrade cannot break it). Because the fix is in the deploy script, every redeploy and every rebuild applies it.

Evidence it worked.

$ curl -s https://dd56jth94yne6.cloudfront.net/api/config
{"appTitle":"AutoHub Assistant", … "serverDomain":"https://dd56jth94yne6.cloudfront.net", … "registrationEnabled":true, …}
$ docker ps --format "{{.Names}} {{.Status}}"
LibreChat Up About a minute · chat-mongodb Up 3 minutes · chat-meilisearch Up 15 seconds

Every redeploy since then has come up with the AutoHub title and a healthy search container (/autohub/deploy log).

INC-02: the assistant could not answer (bad key, then a retired model)

Symptom: every chat showed 400 API key not valid. Cause 1: the stored key was 4 characters long, a mistyped value at the hidden prompt. A second attempt stored 106 characters, because the key was pasted twice and the hidden input showed nothing. Fix 1: the key prompt now strips whitespace and calls Google's models endpoint before saving, and only HTTP 200 is stored. Cause 2: with a valid key, 404 models/gemini-2.5-flash is no longer available to new users. Google retired the model we had configured. Fix 2: we listed the models the key can use, tested gemini-3.5-flash (HTTP 200), set /autohub/gemini_model and redeployed. Lesson: a deployment that has not changed can still break when the provider changes, so validate secrets on entry and test the model name.

INC-03: planned outage to prove the monitoring

Fault injected 9 Nov 01:07:05 UTC (docker compose stop api). Health check failed at 01:10 and 01:15, with CloudFront returning 504. Alarm at 01:16:03, then email. Recovered at 01:20:45 with ./ops.sh redeploy. Time to detect: 8 min 58 s. Time to fix after the alarm: 4 min 42 s.

INC-04: key rotation broke the assistant

A Gemini key was pasted into an AI chat by mistake. Following the brief, it was deleted at once in AI Studio. It was the key AutoHub was using, so answers failed with 401 API key not valid. Our evaluation run found this at about 01:28 UTC, 9 Nov. A new key was created and saved through the validating prompt at 01:33:48, and AutoHub was redeployed at 01:34:02. Prevention: rotation is now a runbook step (below), so the new key is stored before the old one is deleted. Gap: the health check did not catch this, because /health does not call the model. A failed-answer metric is first on Next steps.

Runbook: rotate or replace the Gemini API key

RUNBOOK: Rotate / replace the Gemini API key
Owner: Reighfer Joshua Bondoc   Last tested: 2026-11-09 (INC-04)   Takes: 5 minutes   Ask: Reighfer

1. WHAT THIS IS FOR
   Put a new Google Gemini API key into AutoHub without downtime, e.g. after a key leaked or Google rejected it.

2. HOW YOU KNOW YOU NEED IT
   Chats show "The model provider could not complete this request (status 400/401) … API key not valid",
   or a key was exposed anywhere (chat, screenshot, Git). Command that shows the problem (AWS CloudShell):
     cd ~/autohub-ops && source ./config.env
     K=$(aws ssm get-parameter --name /autohub/gemini_api_key --with-decryption --query Parameter.Value --output text)
     curl -s -o /dev/null -w '%{http_code}\n' -H "x-goog-api-key: $K" https://generativelanguage.googleapis.com/v1beta/models; unset K
   -> anything other than 200 means the stored key is bad.

3. WHAT IT AFFECTS
   Every customer: the site loads and logins work, but every question returns an error. Stored chats are safe.

4. HOW TO DO IT
   Step 1: aistudio.google.com > API keys > Create API key. Copy it. Do NOT delete the old key yet.
   Step 2: in CloudShell run the validating prompt (from the README, "Replace the Gemini key"),
           paste the key ONCE, press Enter        -> you should see "Google accepted the key … KEY SAVED"
   Step 3: it runs ./ops.sh redeploy by itself   -> you should see "[deploy] deployed build …" and "status: Success"
   Step 4: only now delete the old key in AI Studio.

5. HOW TO CHECK IT WORKED
   - [ ] the curl in step 2 of "How you know" prints 200
   - [ ] ask "Which SUVs do you have under 1,000,000 pesos?" and get AH-1027 and AH-1031
   - [ ] no new alarms for 10 minutes

6. HOW TO UNDO IT
   If the new key misbehaves and the old one is not deleted yet, run the prompt again with the old key.
   Parameter Store keeps history: aws ssm get-parameter-history --name /autohub/gemini_api_key

7. GOTCHAS
   - The prompt is hidden: paste once. A double paste gives a key twice as long (INC-02).
   - New AI Studio keys start with "AQ." and are ~53 characters, not "AIza…".
   - Deleting the old key BEFORE saving the new one takes the assistant down (INC-04).
   - Never paste a key into a chat, a ticket or a screenshot. If you do, rotate it with this runbook.

8. CHANGE HISTORY
   2026-11-09 - written after INC-02/INC-04; added "save new key before deleting old".
